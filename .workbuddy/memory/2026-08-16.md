## 排查：雨水收集器可与其他建筑重叠 —— 根因 isEdifice=false（与 Impassable 无关）
- 现象：`MEE_RainwaterCollector`（2x2）能直接盖在墙/生产台等已有建筑上。
- **此前 XML 里的注释断言是错的**：原注释写「本建筑是 Impassable 实心 Building，原版
  CanPlaceBlueprintOver 会返回 SpaceAlreadyOccupied，无需 PlaceWorker」。实际读源码后推翻。
- 真实根因（`GenConstruct.CanPlaceBlueprintOver`，GenConstruct.cs:643）：
  ```csharp
  if (!newThingDef.IsEdifice()) {                    // ← isEdifice=false 走这里
      if (oldDef.building != null && !oldDef.building.canBuildNonEdificesUnder) return false;
      if (newThingDef.EverTransmitsPower && oldDef.EverTransmitsPower) return false;
      return true;                                   // ← 默认放行！
  }
  ```
  而 **`BuildingProperties.canBuildNonEdificesUnder` 默认 = true**（BuildingProperties.cs:73），
  绝大多数建筑都允许非-edifice 压在上面 → 收集器被放行。
  若 `isEdifice=true` 则走 `IsEdificeOverNonEdifice()` 分支：压在墙/其他 edifice 上时
  会落到函数末尾 `return false`，即正确拒绝。
- **关键认知：`passability` 完全不参与建筑重叠判定。** 整个 CanPlaceBlueprintOver 里只有一处
  看 Impassable，且限定 `oldDef.category == ThingCategory.Plant`（不可通行植物）。
  所以「设成 Impassable 就能防重叠」是错的直觉。
- **`BuildingProperties.isEdifice` 默认值是 `true`**（BuildingProperties.cs:12）——
  原来那行 `<isEdifice>false</isEdifice>` 等于主动关掉了原版自带的重叠保护。
- 修复：删掉 `<isEdifice>false</isEdifice>`（恢复默认 true），并加
  `<canBuildNonEdificesUnder>false</canBuildNonEdificesUnder>`（反向也禁止别人把电线/家具
  塞进本建筑格内）。已在 XML 内写详细注释防止再被改回。
- 安全性核对：`isEdifice=true` 不会引入新 ConfigError —— ThingDef.cs:1792 的
  "fillPercent is 1.00 but is not edifice" 仅在 fillPercent=1.00 时触发（本建筑 0.5）；
  BuildingProperties.cs:488/496 两条也都是「非 edifice 才报错」，改 true 更安全。
- 未改动的三个建筑（有意保留 isEdifice=false）：`MEE_WaterWell`/`MEE_WaterExtractor`
  （1x1 Building_WorkTable）与 `Hormones_ExerciseSpot`（1x1）——工作台/点位允许叠在
  地毯等之上是合理设计，与原版制作台一致。
- 纯 XML 改动无需重编 DLL，已 cp 同步 Steam 副本（游戏运行中也安全），需完全重启游戏生效。

## 调研：体魄提升食量 → 一次拿多份食物（只出结论，未改代码）
- 用户诉求：体魄高的小人一次应拿够「当前食量缺口」的份数（缺 2.0 拿 2 份、1.6 也拿 2 份、
  0.8 优先拿 0.8 的食物再拿 1.0），而现在永远只拿 1 份。用户猜逻辑在 Need_Food —— **方向对，
  但真正卡点不在那里**。
- **取食份数完整链路（rimsage 核实 1.6）**：
  1. `FoodUtility.WillIngestStackCountOf(ingester, def, singleFoodNutrition)`（FoodUtility.cs:1273）
     —— 唯一的份数决策入口，被 JobGiver_GetFood:122/126、Toils_Ingest:210(预留)、
     WorkGiver_FeedPatient、Warden_Feed/DeliverFood、JobGiver_EatInGatheringArea、
     FloatMenuOptionProvider_Ingest 等**全部取食路径**调用 → 改这一处即可贯通。
  2. 内部先算 `StackCountForNutrition(needs.food.NutritionWanted, singleNutrition)`
     （FoodUtility.cs:1308）= `Mathf.Max(Mathf.RoundToInt(wanted/single), 1)`。
     ⚠ 是**四舍五入**不是向上取整：缺 1.6 吃 1.0 的餐 → RoundToInt(1.6)=2（符合用户预期）；
     但缺 1.4 → 1 份。若要「不足也补足」需自行改成 CeilToInt。
  3. 然后 `if (def.ingestible.maxNumToIngestAtOnce > 0) num = Min(num, 该值)` ← **真正卡点**。
- **卡点证据**：`Defs/Core/ThingDefs_Items/Items_Food.xml:37` 的抽象基 `MealBaseIngredientless`
  （所有餐食的祖先）硬写 `maxNumToIngestAtOnce=1` + `defaultNumToIngestAtOnce=1`。
  所以哪怕需求量算出 2 份也会被截回 1。
- **第二个必须一起改的卡点**：`Thing.IngestedCalculateAmounts`（Thing.cs:2192-2203）里
  **又做了一次同样的截断**（且这里用的是 `CeilToInt`）。只改 WillIngestStackCountOf 会导致
  「拿了 2 份但只吃 1 份」，剩下那份留在身上/掉地上。两处都要放开才闭环。
- **食量上限其实早已联动体魄**（本次新发现，避免重复实现）：
  `HormonesLogic.cs:101` 已有 `[HarmonyPatch(typeof(Need_Food), MaxLevel, Getter)]` Postfix
  乘 `HormonesLogic.GetAppetiteMultiplier(pawn)`。而 `PhysiqueLgc.GetAppetiteMultiplier`
  实际是 `return GetHungerRate(pawn)`，按阶段返回 Frail 0.80 / Average 1.0 / Fit 1.20 /
  Strong 1.60 / Peak 2.0 → Peak 上限≈2.0 营养。**所以上限不用再做，缺的只是「拿几份」。**
- ⚠ 发现既存设计瑕疵：`Define` 里 `AppetiteBase=0.66/AppetitePerPhysique=0.067/
  AppetiteMinMultiplier=0.66/AppetiteMaxMultiplier=2.0` 四个常量**全未被使用**
  （GetAppetiteMultiplier 直接转发 GetHungerRate）。若要让食欲与饥饿速率解耦需另行实现。
- 另注：`Need_Food.MaxLevel` 在游戏运行时实际取 `StatDefOf.MaxNutrition`，
  故也可用 StatPart 方案替代 Harmony patch（本项目已用 patch，保持现状即可）。

## 实现：体魄 → 一次取用多份食物（向上取整；饥饿速率不动）
- 用户定案：份数用**向上取整**（缺 1.4 也拿 2 份，接受营养溢出）；**暂不解耦食欲/饥饿速率**。
- 新增 `_indexProj/Source/Logic/PhysiqueLogic/PhysiqueEatingPatches.cs`，已加 csproj
  `<Compile Include>`（该工程 EnableDefaultCompileItems=false，漏加会静默不编译）。
- 三个类型：
  - `PhysiqueEatingUtility`：`MaxServings=10` 硬上限（防极端 modded 低营养食物一次搬空）；
    `ShouldAllowMultiServing`（人形 + IsHormoneSubject + 非药物 + 食欲倍率>1.001，即 Fit 及以上
    才启用，Frail/Average 保持原版一份）；`ServingsForNutrition` = `CeilToInt(wanted/single)`
    并 Clamp 到 [1, MaxServings]，单份营养 ≤0.0001 时返回 1 交还原版语义。
  - `FoodUtility_WillIngestStackCountOf_Physique_Patch`（Postfix）：放开"拿几份"。
    用 Postfix 而非 Prefix 以保留原版全部前置判断；**只放大不缩小**（`if (want > __result)`）
    避免与其它 mod 的加量逻辑打架。
  - `Thing_IngestedCalculateAmounts_Physique_Patch`（Postfix）：放开"实际吃几份"，
    同步重算 `nutritionIngested = numTaken * single`，否则吃多份只回一份饱食度。
- **两处必须同时 patch**（本次核心认知）：只改 WillIngestStackCountOf 会"拿 2 份只吃 1 份"，
  余下留身上/掉地上。
- 关键源码依据：`Thing.Ingested` 在 IngestedCalculateAmounts 之后执行
  `if (numTaken == stackCount) 整堆移除 else SplitOff(numTaken)`（Thing.cs:2149-2163）
  → 因此 Postfix 里 **必须 `Min(want, stackCount)`**，否则 SplitOff 超量出错。
- 作用域安全性：`Thing.IngestedCalculateAmounts` 是 protected virtual，`Corpse`(Corpse.cs:324)
  与 `Plant`(Plant.cs:603) 各有 override → patch Thing 基类只影响普通餐食，天然不碰尸体/植物。
- 校验：braces 9/9、parens 35/35；引用的 `FoodUtility.NutritionForEater(Pawn,Thing)`
  (FoodUtility.cs:1636)、`PhysiqueLgc.IsHormoneSubject/GetAppetiteMultiplier` 均已核实存在。
- **未编译未部署**（沙箱无 dotnet + 游戏运行中占用 DLL）。需用户关游戏跑 `copyToRimWorld.bat`。
  待观察：Peak 小人是否一次取 2 份并一次吃完、饱食度回满、无残留食物。

## OnDietEaten 拓展：吃素菜 → 营养 8% 转糖（Need_MEE_Sugar）
- 用户需求：OnDietEaten 事件拓展——当吃的是素菜时，将所获营养值的 8% 转化为糖需求。
- **事件签名拓展（主 mod，破坏性改动但调用方仅 2 处，已同步改）**：
  - `NeedChangeEvents.cs`：`DietEatenHandler(Pawn, float nutritionGained)` → `(Pawn, float nutritionGained, Thing food)`；`FireDietEaten` 同签名。
  - `Patch_Thing_Ingested_DietWater.cs`：Postfix 增加 `Thing __instance` 参数传入被吃的食物实例。

- **模块侧实现（MEEMgr.cs）**：

  - `OnDietEaten` 处理器改为：① 无论荤素 `water.Satisfy(nutritionGained * 0.15)`（原有 15% 水分保留）；② 素菜判定 `FoodUtility.GetFoodKind(food) == FoodKind.NonMeat`（纯植物、无肉无蛋奶，与上一轮确认的素食口径一致）→ `sugar.Satisfy(nutritionGained * 0.08)`。糖变化经 OnSugarChanged 自动飘字。
